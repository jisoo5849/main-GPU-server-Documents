DESIGN DOC · v1.1

메인 GPU 서버 설계서

  • 작성일 2026-10-23
  • 상태 설계 확정, 구현 전
  • 대상 서버 main (Ubuntu, GPU 1장 72GB)
  • 사용자 2~3명, 사무실 LAN

사무실 작업자들이 브라우저로 ComfyUI를 자유롭게 쓰되, 모든 연산은 메인의 GPU 한 장에서 접수 순서대로 하나씩 처리하는 서버입니다. 사용자마다 독립된 작업공간을 두고, 실행 버튼을 누른 순간의 환경을 그대로 고정해서 실행합니다.

1목표와 원칙

핵심 원칙: 작업자 PC는 화면만 쓰고, 연산은 전부 메인에서 합니다.

  • 편집은 각자 동시에, GPU 실행은 메인 전체에서 한 번에 한 건만 합니다.
  • A가 노드를 바꿔도 B의 환경은 바뀌지 않고, A가 이미 접수한 작업도 바뀌지 않습니다.
  • 모든 실행 요청은 DB를 거칩니다. DB를 거치지 않고 GPU에 닿는 경로를 두지 않습니다.

2요구사항

항목요구사항설계 반영
작업자 PC화면만 사용, 설치 없음브라우저로 http://main 접속
사용자 계정2~3개의 개인 계정허브 로그인, 비밀번호는 argon2id 해시로 저장
ComfyUI 환경사용자별 독립, 필요하면 프로젝트별 추가환경마다 ComfyUI · 커스텀 노드 · Python을 따로 두고 Docker로 실행
커스텀 노드각자 설치하고 버전 관리각자의 편집 공간에서 ComfyUI-Manager로 설치
환경 고정대기 중인 작업은 접수 때의 환경으로 실행실행 버튼을 누를 때 스냅샷을 찍어 그 버전으로 실행
모델 파일공용 저장소에서 공유/srv/models 하나를 모든 컨테이너에 읽기 전용으로 연결
GPU 사용메인 전체에서 한 번에 한 작업만GPU 실행 공간은 항상 최대 1개, 편집 공간에는 GPU 장치 자체가 없음
작업 기록사용자 · 모델 · 워크플로우 · 결과PostgreSQL에 접속 로그, 작업, 사용 모델, 시간, 결과 파일 기록
결과 확인ComfyUI 화면, 웹 이력, 네트워크 폴더실행 직후 자기 화면에 표시, 공유 이력 페이지, Samba \\main\results
열람 범위모두가 함께 공유, 누구나 수정·작업 가능이력 페이지와 Samba에서 전원 열람, Samba 폴더는 전원 읽기·쓰기 (삭제 파일은 휴지통에 30일 보관)
설치 방식Windows에서 개발, Ubuntu에 Docker로 설치docker compose와 설치 스크립트로 배포

3전체 구조

편집하는 곳과 실행하는 곳을 나눕니다. 편집 공간은 사용자 수만큼 늘 켜져 있지만 GPU가 없습니다. GPU 실행 공간은 허브가 순서가 된 작업 하나를 위해서만 띄웁니다.

4작업 처리 순서

요청 순서대로 처리합니다. 앞 작업의 메모리 해제가 확인되기 전에는 다음 작업을 시작하지 않습니다.

  1. A · B · C가 동시에 워크플로우를 편집합니다.편집 공간에는 GPU가 없으므로 편집은 서로 영향을 주지 않습니다.
  2. 실행 요청을 접수 순서대로 DB에 저장합니다.허브가 실행 버튼 요청을 가로채 검증하고, 환경 스냅샷을 찍고, 순번(seq)을 붙여 PostgreSQL에 넣습니다. 화면에는 바로 "대기 중"으로 표시됩니다.
  3. 스케줄러가 맨 앞 작업의 사용자 · 환경 · 모델을 확인합니다.환경 버전 스냅샷이 남아 있는지, 필요한 모델 파일이 접수 때와 같은지 봅니다. 문제가 있으면 실행하지 않고 이유를 기록합니다.
  4. 해당 환경 버전으로 메인 GPU에서 실행합니다.직전 작업과 환경 버전이 같으면 켜 둔 실행 공간을 다시 쓰고, 다르면 새로 띄웁니다. 진행률과 미리보기는 작업자 화면으로 그대로 전달됩니다.
  5. 결과와 사용 기록을 저장하고, 실행 종료와 메모리 해제를 확인합니다.GPU 메모리가 기준치 이하로 돌아왔는지 메인에서 직접 측정합니다. 내려가지 않으면 단계적으로 강하게 정리합니다.
  6. 다음 작업을 실행합니다.

5구성 요소

구성 요소프로그램역할
허브Python FastAPI (직접 개발)로그인, 모델 선택 화면, 환경별 화면 중계, 실행 접수와 스냅샷, 스케줄러, 진행 상황 전달, 메모리 해제 확인, 이력 페이지
권한 도우미root 소유 스크립트 1개스냅샷 생성·삭제, Samba 비밀번호 등 관리자 권한이 필요한 작업만 고정된 인자로 수행
DBPostgreSQL 18계정, 접속 로그, 작업 대기열, 환경 버전, 사용 모델, 결과, GPU 점유 상태
컨테이너Docker Engine + NVIDIA Container Toolkit (CDI)편집 공간과 실행 공간 실행. GPU는 허브가 명시적으로 요청한 실행 공간에만 연결
ComfyUI 이미지자체 Dockerfile (CUDA 13 기반)OS와 CUDA 공통 층. ComfyUI · 노드 · Python 패키지는 각 환경 폴더에 둠
LLM · 임베딩Ollama허브의 중계 포트(11434) 뒤에 두고 같은 대기열로 처리
채팅 화면 (선택)Open WebUILLM 모델 선택과 채팅. 요청은 허브를 거침
공유 폴더Samba결과 폴더(전원 읽기·쓰기, 휴지통 포함), 모델 업로드 폴더
스냅샷 저장소btrfs 전용 파티션환경 버전을 순간 복사로 고정. 실제로 바뀐 부분만 공간을 차지

Redis · Celery를 쓰지 않는 이유

  • GPU가 1장이고 실행은 한 번에 한 건이므로, 여러 일꾼(worker)에 작업을 나눠 주는 Celery의 장점이 쓰이지 않습니다.
  • 대기열과 작업 기록을 PostgreSQL 한 곳에 두면 "대기열에는 있는데 기록에는 없는" 불일치가 생기지 않습니다. 순서는 DB 순번(seq)과 잠금으로 보장하고, 새 작업 알림은 PostgreSQL의 LISTEN/NOTIFY로 받습니다.
  • Celery는 작업을 미리 가져가거나 재시도하면서 순서가 바뀔 수 있어, 엄격한 접수 순서 처리를 위해 별도 설정과 점검이 더 필요합니다.
  • 추가를 검토할 시점: GPU나 서버가 여러 대로 늘거나, 허브를 여러 개 띄우거나, LLM 요청이 초당 수백 건 수준으로 늘 때입니다.

6환경 분리와 버전 고정

환경 하나에 들어 있는 것

  • ComfyUI 본체 (git checkout)
  • custom_nodes/ 전체
  • Python 가상환경 (torch, 노드 의존성 등 모든 패키지)
  • OS · CUDA 이미지 버전 (digest)

환경 밖에 두는 것

  • 모델 파일 (공용 저장소, 접수 때 경로·크기·해시를 기록)
  • 업로드한 입력 이미지 (접수 때 작업 전용 사본으로 고정)
  • 사용자 설정, 저장한 워크플로우, 캐시

실행 버튼을 누를 때

  1. 노드 설치나 업데이트가 진행 중이면 끝날 때까지 기다린 뒤 진행합니다. 설치하다 만 상태가 고정되는 것을 막기 위해서입니다.
  2. 직전 버전 이후 환경이 바뀌었는지 확인합니다. 바뀌지 않았으면 직전 버전을 그대로 씁니다.
  3. 바뀌었으면 읽기 전용 스냅샷을 새로 찍습니다. 몇 초 안에 끝나고, 바뀐 부분만 공간을 차지합니다.
  4. 작업에 그 버전 번호를 기록합니다. 이후 노드를 업데이트해도 이 작업은 이 버전으로 실행됩니다.

버전 관리

  • 버전마다 ComfyUI 커밋, 노드 목록과 커밋, pip freeze를 기록합니다.
  • 모델 선택 화면의 "내 환경"에서 버전 목록, 이전 버전으로 되돌리기, 프로젝트용 환경 복제를 제공합니다.
  • 대기 중인 작업이 참조하지 않고 보관 표시도 없는 오래된 버전은 주기적으로 정리합니다.

7GPU 한 건 규칙 보장 장치

규칙이 한 곳에만 의존하지 않도록 여러 겹으로 막습니다.

장치막는 것
편집 공간에 GPU 장치를 연결하지 않음 (--cpu, GPU 미할당, 시작 시 점검)사용자가 설치한 노드가 큐 밖에서 GPU를 쓰는 것
GPU는 허브가 띄운 실행 공간에만 연결, 실행 공간은 항상 최대 1개두 작업이 동시에 GPU를 쓰는 것
DB 단일 순번(seq)과 단일 스케줄러 잠금순서 뒤바뀜, 스케줄러 중복 실행
DB 규칙: "실행 중" 상태 작업은 1건만 존재 가능 (고유 인덱스)프로그램 오류로 두 건이 동시에 실행 상태가 되는 것
컨테이너 네트워크 분리 (편집 공간끼리, 편집 공간과 실행 공간 사이 접속 차단)노드가 실행 공간에 몰래 작업을 보내 대기열과 기록을 건너뛰는 것
실행 공간은 허브가 발급한 작업 표가 있는 요청만 받음네트워크 차단이 뚫렸을 때의 두 번째 방어
GPU 감시: 허용되지 않은 프로세스가 GPU 메모리를 쓰면 기록하고 차단예상하지 못한 경로
사용자에게 서버 터미널 · Docker 권한을 주지 않음사람이 직접 GPU 프로그램을 실행하는 것

장애 상황

  • 실행 공간이 죽거나 멈춤: 컨테이너 종료와 GPU 활동으로 판단해 작업을 실패로 기록하고, 메모리를 확인한 뒤 다음 작업으로 넘어갑니다.
  • 허브 재시작: 실행 중이던 작업은 DB와 실행 공간 상태를 보고 다시 이어받습니다. 대기 중 작업은 원래 순번을 유지합니다.
  • 편집 공간이 Manager로 재시작: 편집 화면만 잠시 끊깁니다. 대기 중인 작업은 이미 고정된 버전으로 실행되므로 영향이 없습니다.
  • 긴 영상 작업: 최대 실행 시간과 멈춤 감지 시간을 설정값으로 둡니다.

8메모리 해제 확인

ComfyUI의 자체 보고를 믿지 않고, 메인에서 GPU 메모리를 직접 측정합니다(NVML).

단계조치통과 조건 (기본값)
1모델 내리기 (/free unload_models), Ollama 모델 내리기실행 공간 사용량 ≤ 기본 점유 + 512MB, 전체 ≤ 유휴 기준 + 기본 점유 + 768MB, Ollama 로드 모델 0개 (최대 30초 대기)
2캐시까지 비우기 (/free free_memory)위와 같음 (30초)
3실행 공간 종료GPU 프로세스 0개, 전체 ≤ 유휴 기준 + 256MB (60초)
4대기열 정지 (BLOCKED), 관리자 알림관리자가 확인 후 재개. 대기 중 작업은 그대로 보존

작업마다 최대 VRAM, 작업 후 VRAM, 정리 방법, 정리 시간을 기록합니다. 기준값은 설정으로 바꿀 수 있습니다.

9LLM · 임베딩

  • 허브가 Ollama와 같은 주소 형식(11434 포트)의 중계를 열고, 실제 Ollama는 메인 내부에만 둡니다.
  • 모델 목록 조회는 GPU를 쓰지 않으므로 바로 응답합니다. 생성 · 채팅 · 임베딩 요청은 ComfyUI 작업과 같은 대기열에 들어갑니다.
  • 워크플로우 안에서 Ollama를 부르는 경우: 지금 GPU를 쓰고 있는 실행 공간에서 온 호출은 대기열에 다시 넣지 않고 바로 처리합니다. 자기 차례를 자기가 기다리는 교착을 막기 위해서입니다. 이 호출은 부모 작업에 묶어 기록합니다.
  • 작업이 끝날 때는 새 내부 호출을 먼저 막고, 진행 중인 내부 호출이 끝난 뒤에 메모리를 확인합니다.
  • 사용자별 API 키를 발급합니다. 스크립트에서 호출해도 누가 썼는지 기록됩니다.
  • Ollama 설정: OLLAMA_KEEP_ALIVE=0, OLLAMA_MAX_LOADED_MODELS=1, OLLAMA_NUM_PARALLEL=1

10결과물 · 이력 · 공유 폴더

/srv/results/<사용자>/<프로젝트>/<YYYY-MM-DD>/<파일명>_00001_.png
                                            <job_id>.json   (워크플로우, 사용 모델, 환경 버전, 시간)
  • 실행 직후: 자기 ComfyUI 화면의 노드에 결과가 바로 표시됩니다.
  • 웹 작업 이력 (http://main/history): 모든 사용자의 작업을 썸네일과 함께 보여 줍니다. 사용자 · 프로젝트 · 모델 · 날짜로 거르고, "내 ComfyUI에서 이 워크플로우 열기"와 "같은 환경 버전으로 다시 실행"을 제공합니다.
  • 네트워크 폴더: Windows에서 \\main\results를 드라이브로 연결합니다. 누구나 모든 결과물을 열고, 수정하고, 새 파일을 넣고, 폴더를 정리할 수 있습니다.
  • 실수 대비 휴지통: 네트워크 폴더에서 지운 파일은 바로 사라지지 않고 \\main\results\.recycle\<사용자>\에 30일간 보관됩니다. 같은 이름으로 덮어쓴 파일도 이전 판이 휴지통에 남습니다.
  • 권한 통일: 생성 결과와 사용자가 넣은 파일 모두 같은 그룹(comfyusers)의 읽기·쓰기 권한으로 맞춰, 누가 만든 파일이든 다른 사람이 고칠 수 있게 합니다.
  • 이력과 파일이 달라질 때: 웹 작업 이력은 생성 당시 기록(워크플로우, 모델, 원래 파일명)을 DB에 그대로 보존합니다. 파일이 지워지거나 옮겨지면 이력에 "파일 없음"으로 표시하고, 수정된 파일은 현재 파일을 보여 줍니다.
  • 모델 추가는 \\main\model-inbox에 올리면 허브가 검사한 뒤 공용 저장소로 옮깁니다. 교체되거나 지운 모델은 14일간 보관합니다.

13설계 검토 결과

설계안 3개를 독립적으로 만든 뒤 실용성 심사, 기술 정확성 심사, 레드팀 점검을 거쳤습니다. 근거가 된 사실은 ComfyUI v0.42.5 소스 코드와 각 도구의 최신 문서로 확인했습니다.

설계안방식실용성기술판정
편집 · 실행 겸용편집 공간이 GPU를 가진 채 순서가 오면 직접 실행5.86.6탈락
편집 · 실행 분리GPU 없는 편집 공간 + 고정 버전 실행 공간 (ZFS)5.48.0보안 장치 채택
단순 운영안같은 분리 구조를 허브 하나로 단순화 (btrfs)6.46.4기본 구조 채택

겸용안 탈락 이유: 편집 공간이 항상 GPU를 갖고 있어, 다른 사용자의 노드가 작업 도중 GPU 메모리를 잡아도 막을 수 없고 사후에 감지만 가능합니다.

레드팀 지적을 반영한 보완

  • 컨테이너 간 네트워크를 차단했습니다. 이 차단이 없으면 노드가 실행 공간에 직접 작업을 보내 대기열과 기록을 건너뛸 수 있었습니다.
  • 노드 설치 중에는 스냅샷을 찍지 않고, 설치가 끝난 뒤 찍습니다.
  • 환경 변경을 감지할 때 파일 삭제까지 잡도록 바꿨습니다. btrfs의 find-new 대신 세대 번호를 비교합니다.
  • 입력 이미지도 접수 때 작업 전용 사본으로 고정합니다.
  • DB 고유 인덱스로 "실행 중 1건"을 이중으로 보장합니다.
  • 워크플로우 내부 Ollama 호출이 끝나기 전에 메모리를 확인하지 않도록 순서를 정했습니다.
  • 허브가 재시작돼도 실행 중 작업을 다시 이어받습니다.
  • 결과 파일 권한을 그룹 읽기·쓰기로 통일해 공유 작업이 깨지지 않게 하고, 누구나 수정할 수 있는 대신 휴지통으로 실수를 되돌릴 수 있게 했습니다.
