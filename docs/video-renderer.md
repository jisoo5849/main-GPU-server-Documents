# 영상용 렌더러 (2026-11-11, v1)

제작진 모드와 프롬프트 도우미가 만든 이미지 프롬프트와 별도로, 영상 모델(Wan 2.2 I2V·T2V)에 맞는 '움직임 프롬프트'를 쓰는 단계다.
v1 코드는 이 저장소에 있고 개발 PC 의 단위 테스트로만 확인했다. **메인 실기기에서는 아직 실행하지 않았다.**
11-11 에 러다이트처럼 한 줄 요청을 네 단락의 영어 상세 프롬프트로 쓰는 **장문 프로필**을 더해 기본값으로 두었다(13절).

## 1. 왜 필요한가

- 지난 영상 시험(Wan 2.2 I2V, 도우미 5편 + 제작진 5편)은 이미지 프롬프트 끝에 같은 문장("카메라가 천천히 다가가며 은은하게 움직인다")을 덧붙여 영상을 만들었다.
  - 백엔드에 영상용 프롬프트 기능이 없어서 그렇게 했다. 그래서 그 시험은 '제작진 모드의 효과'가 아니라 '이미지 + I2V 가 이어지는지'만 보여 준다.
- I2V 는 첫 화면 이미지가 외형(대상, 조명, 색, 구도)을 정한다. 프롬프트가 할 일은 **무엇이 어떻게 움직이는가**와 **카메라가 어떻게 움직이는가**다.
  - 이미지 프롬프트는 정지 장면의 외형을 길게 설명하는 글이라 영상 모델에 그대로 넣으면 움직임 지시가 약하다.
- 제작진 모드의 단계(배경, 조명, 색, 장르)에는 카메라 움직임, 속도, 마무리 칸이 없었다. 러다이트 예시의 "카메라가 천천히 다가간다"에 해당하는 부분이다.
- 사용자 의도 최우선 원칙(11-11 개편)을 영상에도 그대로 적용한다. 예: '천천히', '드론', '360도', '루프'를 사용자가 쓰면 선택과 글 모두에서 지킨다.

## 2. v1 범위 (11-11 결정)

| 포함 | 제외 (v2 이후) |
|---|---|
| Wan 2.2 I2V 단일 클립, Wan 2.2 T2V 단일 클립 | 컷 구성(두 컷·세 컷, 클립 나눠 잇기) |
| 첫 화면 이미지를 시각 모델로 읽기 | LTX 프로필과 사운드 칸 |
| 프레임 수·fps 는 **제안만** 표시 (노드에 자동으로 넣지 않음) | |

## 3. 흐름

```
I2V: 요청(도우미 칸) + 첫 화면(LoadImage) → [시각 모델: 첫 화면 읽기] → [확장 모델: 영상 제작진 초안 → 검사 → 고쳐 쓰기] → 움직임 프롬프트
T2V: 요청(도우미 칸) → [확장 모델: (도우미 결과가 없으면) 장면 확장 → 영상 제작진 초안 → 검사] → 장면 + 움직임 + 그림체 고정 문장
장문: 위와 같은 경로에서 초안만 네 단락의 장문으로 받는다 → 네 단락 (+ T2V 그림체 문장)   (13절)
```

- 움직임만 프로필은 외형을 다시 쓰지 않는다. I2V 결과는 움직임 문장뿐이고 그림체 고정 문장도 붙이지 않는다(첫 화면이 이미 정했다).
- T2V 는 첫 화면이 없으므로 장면이 필요하다. 패널의 도우미 확장 결과가 있으면 그것을 쓰고, 없으면 같은 GPU 차례 안에서 도우미(제작진 모드 포함)로 장면부터 쓴다(`promptx.expand_in_turn`).
- 허브는 워크플로우를 만들지 않는다. 결과 글과 설정 제안만 돌려주고, 패널이 긍정 프롬프트 노드를 찾아 넣는다(14절, 이미지 도우미와 같다).

## 4. 영상 제작진 단계

요청이 제품·공간·풍경이면(이미지 제작진과 같은 `crew.route`) 단계 메뉴에서 고른다. 그 밖의 요청(사람, 캐릭터 정본, 손 숨김, 분야 없음)은 메뉴 없이 규칙과 '선택 아이디어'만으로 쓴다.
단계는 `hub/app/video_knowledge.json` 에 있고, 메뉴 재료는 라이브러리의 `video_motion` 칸(1,132개)을 묶음으로 나눠 쓴다(`crew_lib.retrieve` 의 `only`).

| 단계 | 제품 | 공간 | 풍경 |
|---|---|---|---|
| 카메라 | camera_* (7묶음) | camera_* | camera_* |
| 대상 움직임 | product_motion, liquid_motion, fabric_hair_motion | light_motion, fabric_hair_motion, liquid_motion, urban_motion | nature_motion, liquid_motion |
| 환경 움직임 | light_motion, air_particle_motion, liquid_motion, still_background | air_particle_motion, light_motion, still_background | air_particle_motion, light_motion, urban_motion, still_background |
| 속도 | pacing | pacing | pacing |
| 마무리 | ending_state, loopable | ending_state, loopable | ending_state, loopable |

- 단계마다 8개 안팎을 요청마다 새로 뽑는다. 사용자 영상 말과 맞는 항목을 먼저 넣고, 한 단계에 요구가 둘이면(예: '천천히 다가가는') 둘 다 맞는 항목을 먼저 넣는다.
- 환경 움직임에는 늘 '배경은 고요하게'(still_background) 선택지가 있다. 모든 영상이 배경까지 움직이지 않게 하려는 것이다.
- 요청에 사람이 없으면 사람이 나오는 항목은 뺀다(기존 거름). 글자·로고·간판을 지시하는 항목 7개(라벨 클로즈업, 네온 간판 등)는 영상 메뉴에서 늘 뺀다.
- 메뉴 항목은 '움직임 방식 · 예시 대상'(예: '15도 작은 호 이동 · 향수병')이다. 지시문은 예시 대상이 아니라 이 요청의 대상에 방식을 적용하라고 한다.

### 라이브러리 보강 (11-11)

설계 때 모자랐던 칸에 16개를 직접 썼다(검사 스크립트 통과).

| 더한 것 | 개수 |
|---|---:|
| 풍경 다가가기·물러나기 (원래 4개) | 6 |
| 풍경 고정 카메라 (원래 2개) | 4 |
| 공간·제품 고정 카메라 | 4 |
| 배경은 고요하게 (새 묶음 still_background) | 2 |

### 사용자 영상 말 (`crew_intent.json`)

영상 의도 15개를 더했다(11-11 1인칭 포함, 사전 전체 163개). 영상 렌더러만 이 말을 요구로 보고, 이미지 확장과 이미지 제작진은 보지 않는다.

| 종류 | 말 (예) | 확인어 (예) |
|---|---|---|
| 카메라 | 다가가는·줌인, 멀어지는·줌아웃, 드론·항공, 360도·오빗, 회전하는, 패닝, 틸트, 고정 카메라·삼각대, 핸드헬드, 따라가는 | push in, pull back, drone, orbit, rotates, pan, tilt, static, handheld, tracking |
| 속도 | 천천히, 슬로모션, 빠르게·역동적 | slow, slow motion, fast |
| 마무리 | 루프, 반복되는 | loop, seamless |
| 시점 | 1인칭·1인칭시점·일인칭·POV·first person | first-person, point of view, pov, through the eyes |

- 날씨·시간 말(눈 오는, 비 오는, 안개 …)도 영상 글에 보여야 한다. 눈·비·안개는 움직이는 것이기 때문이다.
- 장르·색·조명·분위기 말은 첫 화면이 이미 따르므로 검사하지 않고 "움직임이 어긋나지 않게" 알려만 준다. T2V 장문은 예외다(장면 글을 붙이지 않으므로 지킨다, 13절).
- 영상 항목은 태그가 '드론 비행' 같은 구절이라 낱말 태그로는 거의 잡히지 않아, 영문 문장의 확인어로도 요구 항목을 찾는다.

## 5. 초안 검사 규칙 (`video.check_video`)

| 규칙 | 막는 것 |
|---|---|
| 메뉴 id | 단계마다 그 요청의 메뉴 안에서 하나. 대상 움직임과 환경 움직임은 서로 다른 항목 |
| 사용자 영상 말 (선택) | 그 말과 맞는 항목이 메뉴에 있었으면 어느 단계에서든 하나는 골라야 한다 |
| 사용자 말 (글) | 영상 말과 날씨 말마다 확인어가 글에 낱말로 있어야 한다. T2V 는 장면 + 움직임을 함께 본다 |
| 외형 반복 금지 | 첫 화면(장면) 프롬프트와 6낱말 이상 연달아 같은 구절 |
| 카메라 이동은 하나 | 다가가기·물러나기·패닝·오빗·트래킹·크레인(틸트 포함) 중 둘 이상을 섞은 경우 [추정]. 주어가 카메라일 때만 세고, 사용자가 이동을 둘 썼으면 둘까지 허용한다 |
| 한 컷 | cut to, scene change, transition to 같은 장면 전환 |
| 길이 | I2V 25~90 낱말, T2V 움직임 부분 20~70 낱말 [추정] |
| 사람 | 요청에도 첫 화면에도 사람이 없는데 사람·손을 넣은 경우 |
| 손 숨김, 글자·로고, 부정어, 영문만, 한국어 설명 3칸 | 이미지 제작진과 같다 |

- 걸리면 한 번(`VIDEO_REPAIR_ROUNDS`) 고쳐 쓰게 한다. 제작진 단계 초안이 끝내 걸리면 메뉴 없이 다시 쓰고 패널에 알린다. 남은 위반은 패널에 그대로 보여 준다.

## 6. 첫 화면 읽기

- 패널이 화면의 LoadImage 노드(선택한 것 우선)에서 첫 화면 파일을 찾아 보낸다. 입력 폴더 또는 결과 폴더(`[output]`)의 이미지만 읽고, 폴더 밖 경로는 거부한다.
- 시각 모델(`VIDEO_FRAME_MODEL`, 비우면 `IMAGE_INSPECT_MODEL` = qwen3-vl:8b-instruct)이 대상, 위치, 배경, 사람 수, 움직일 수 있는 것, 샷을 JSON 으로 돌려준다. 긴 변 1024px 로 줄여 보낸다.
- 시각 모델이 확장 모델과 다르면 GPU 차례를 한 번 더 쓴다(한 차례에는 모델 하나만 올린다). 같은 모델이면 한 차례 안에서 처리한다.
- 파일을 못 찾거나 못 열거나 시각 모델이 실패해도 글만 보고 계속 쓰고 패널에 알린다. 패널의 체크를 끄면 읽지 않는다. 40MB 넘는 파일은 읽지 않는다.
- 첫 화면을 읽지 않았으면 그림에 사람이 있는지 모르므로 '사람 금지' 규칙을 적용하지 않는다.

| wan22_t2v_mid | 미시험 | 같은 네 단락을 짧게, 170~260낱말, 단락 최소 30, 밀도 예시 없음 (14절) | wan22_t2v 와 같음 |

| wan22_i2v | 모델은 지난 영상 시험에서 씀 (렌더러 글은 미시험) | 짧은 움직임 문장: 카메라 → 대상 → 배경 → 마무리 | 16fps, 최대 81프레임(약 5초), 4n+1 프레임 |
| wan22_t2v | 모델 파일만 있음, 미시험 | 장면 다음에 움직임 문장 | 16fps, 최대 81프레임 [추정: I2V 와 같다고 봄] |

- 코드는 모델 이름을 모른다. 프로필을 더하면 패널 목록에 나온다(`GET /mgs/api/video_profiles`).
- 지난 영상 시험의 Wan 2.2 I2V 구성: 14B 고·저노이즈 fp8 + lightx2v 4스텝 LoRA, cfg 1, shift 5, 640×640, 81프레임, 16fps, 한 편 약 1분 반.
- 길이를 모델 한계보다 길게 적으면 81프레임으로 맞추고 "클립을 나눠 이어 붙여야 한다"고 알린다.

## 8. API와 패널

- `POST /mgs/api/expand_video` (환경 포트, 로그인 쿠키)
  - 받는 값: `text`, `notes`, `style`, `crew`, `profile`, `seconds`, `image`({filename, subfolder, type}), `image_prompt`, `read_frame`
  - 돌려주는 값: `prompt`(최종), `motion`, `scene`(T2V), `ko`(카메라·움직임·시간 설명), `crew`(고른 항목), `frame`(첫 화면 읽기), `settings`(프레임·fps·초), `violations`, `advice`, `rounds`, `long`(장문 여부), `parts`(장문 네 단락, 아니면 null)
  - 장문에서 `motion` 은 네 단락 전체이고, T2V 의 `scene` 은 참고로 쓴 도우미 글일 뿐 `prompt` 에는 들어가지 않는다. `profile` 은 실제로 쓴 프로필이다(I2V 장문이 움직임만으로 바뀌면 `wan22_i2v`)
  - 접속 기록: `video_expand` (프로필, 회차, 남은 위반 수, 첫 화면 사용 여부, 제작진 분야·사용 여부)
- 패널: '영상 프롬프트' 카드(도우미 카드 아래)
  - 요청·꼭 지킬 특징·그림체·제작진 모드 체크는 도우미 칸의 값을 그대로 쓴다. 도우미 확장 결과가 있으면 `image_prompt` 로 함께 보낸다.
  - 프로필, 길이(초), 첫 화면 읽기 체크(I2V)를 고르고 '영상 프롬프트 만들기'를 누른다.
  - 결과: 영상 제작진 고른 항목, [카메라][움직임][시간] 설명, 첫 화면 읽기 요약, 프롬프트, 권장 설정, 위반·안내, 복사·긍정 프롬프트 노드에 넣기, 규칙 경고는 한국어로 풀어 쓰고 자동으로 고치기 버튼을 준다(14절)

## 13. 장문 프로필 (러다이트 감독 agent 식, 11-11)

### 왜

- 러다이트 Agent 모드('감독')는 한국어 한 줄을 승인용 계획 카드로 보여 준 뒤, 영상 모델에는 **구도 → 카메라·빛·룩 → 시간 순서의 움직임 → 마무리** 네 단락의 영어 프롬프트를 넘겼다. 단락마다 약 100낱말(94·102·108·113), 합계 약 417낱말에 사운드 설명 42낱말이 붙었다. 생성 상세 화면에서 원문을 확인했다(Directing_follow_for_comfyUI 02번 문서 E1-c, 03번 3-3).
- 기존 렌더러는 움직임만 25~90낱말(I2V), 장면 + 움직임 20~70낱말(T2V)이라 짧다. 사용자 요청의 핵심은 **장문 + 디테일**이다. 기존 렌더러 구조(사용자 말 최우선, 영상 제작진 메뉴, 첫 화면 읽기, 규칙 검사, 패널 카드)는 그대로 두고 **프로필을 더했다.**

### 무엇이 바뀌나

| 항목 | 움직임만 (wan22_i2v·wan22_t2v) | 장문 (wan22_i2v_long·wan22_t2v_long) |
|---|---|---|
| 글 | 한 단락, 움직임 중심 | 네 단락: `shot` → `camera_light` → `action` → `ending` (아래 표) |
| 받는 방식 | `prompt` 한 칸 | 단락 네 칸을 따로 받고 코드가 이 순서로 빈 줄을 두고 잇는다(모델이 순서를 바꾸거나 단락을 빼먹지 않게) |
| 길이 | I2V 25~90, T2V 움직임 20~70낱말 | T2V 300~450(목표 약 375, 단락마다 약 90), I2V 220~380낱말, 단락마다 50낱말 이상 |
| 외형 | 다시 쓰지 않음(외형 반복 검사) | 함께 씀. T2V 는 도우미 확장 결과를 'LOOK REFERENCE' 로 두고 다시 써도 됨. I2V 는 첫 화면 메모(빛·색 포함)와 참고 글에 있는 말로만 |
| 밀도 예시 | 없음 | T2V 지시문에 직접 쓴 예시 한 편(찻잔, 4단락 362낱말)을 넣는다. I2V 에는 넣지 않는다(예시의 빛·색을 따라 쓰지 않게) |
| T2V 최종 글 | 장면 + 움직임 + 그림체 문장 | 네 단락 + 그림체 문장(마지막 단락). 장면 글은 붙이지 않는다 |

단락마다 쓰는 것 (`video_knowledge.json` 의 `long.parts`, I2V 는 `spec_i2v`):

| 단락 | 담는 것 |
|---|---|
| shot | 매체·룩, 샷 크기, 시점, "one continuous shot" → 전경·중경·배경 구성, 대상의 모양·재질·자세, 장소, 렌즈 원근·심도, 시각적 위계(무엇을 먼저·다음·마지막에 보는지) |
| camera_light | 카메라 이동 하나(또는 고정)의 방향·속도·거리 → 광원·방향·질·색과 그 빛이 재질에 닿는 방식(하이라이트·그림자·반사), 대기(안개·입자·날씨), 색 톤, 매체의 마감(실사는 필름 룩, 수채화·애니 등은 그 매체의 질감이고 필름 말은 쓰지 않는다) |
| action | 시작 순간 → 하나뿐인 주 행동이 펼쳐지는 경로·속도, 빛·표면·주변이 반응하는 모습(물리적으로). 다른 사건은 더하지 않는다 |
| ending | 그 행동이 끝나는 방식(차분한 마지막 화면, 루프면 처음 상태로 이어짐), 마지막 구도(루프면 처음 구도·빛으로, 멈춤 없이), 배경의 잔잔한 움직임, 그대로 유지되는 것(긍정형으로) |

- 장문 규칙(`long.rules`): 감독이 촬영감독에게 설명하듯 길고 구체적으로, 화면에 보이는 것만 쓴다 / 요청이 비워 둔 것만 채운다 / 빛·렌즈·각도·색을 영화 용어로(첫 화면이 있으면 메모·참고 글에 있는 것만), 그림체가 정해져 있으면(STYLE 줄·참고 글·첫 화면) 그와 어긋나는 매체·화풍 말은 쓰지 않는다, 품질 유행어 금지 / 전경·중경·배경과 시각적 위계(첫 화면이 있으면 메모·참고 글에 있는 것만) / 짧은 클립은 주 행동 하나를 세 박자로(루프면 카메라는 고정하거나 처음 자리로, 빛은 그대로), 남는 낱말은 사건이 아니라 그 행동의 모습에 / 1인칭 규칙 / 상표 대신 generic.
- 공통 규칙(모든 프로필): 끝의 짧은 멈춤은 루프가 아닐 때만 괜찮다, 안정성은 긍정형으로만 쓰고 morphing·warping 같은 실패 말을 쓰지 않는다, 글자·숫자·간판·로고·라벨·엠블럼·화면 표시를 쓰지 않는다(네온 간판은 neon lights, 계기·화면·포장은 은은하게 빛나는 면으로).
- 프로필 목록에서 장문 두 개를 맨 앞에 두었다. 프로필을 안 고른 요청과 처음 쓰는 패널은 `wan22_i2v_long` 을 쓴다. 전에 패널에서 다른 프로필을 골랐던 사람은 그 선택이 남아 있으니 목록에서 장문을 한 번 고른다.

### 장문에서 따로 처리하는 것

- **T2V 장문은 사용자의 장르·색·조명·분위기 말도 지킨다.** 장면 글을 앞에 붙이지 않으므로 이 글이 외형의 전부다. 그래서 '사이버펑크', '네온 조명' 같은 말을 USER WORDS 로 주고 검사한다(움직임만 프로필과 I2V 는 전처럼 날씨·시간 말만).
- **T2V 장문에는 그림체를 알려 준다.** 패널의 그림체 칸 글은 끝에 그대로 붙으므로 "STYLE (끝에 붙는다, 반복하지 말고 모든 룩 말을 이와 맞게)" 줄로 넘긴다.
  - 2차 검토 후: STYLE 줄은 "shot 첫머리에 이 매체를 짧게 밝히고, 빛·색·질감을 그 매체 방식으로 쓰고, 어긋나는 실사·필름 말은 쓰지 않는다" 로 바꿨다. 예전 "반복하지 말라" 는 "첫머리에 매체를 쓰라" 는 규칙과 부딪쳐 화풍이 끝에 붙는 한 줄로만 남을 수 있었다. 밀도 예시도 실사 예시라고 밝혀 필름 마감('fine grain', 'film look')을 옮기지 않게 했다.
- **I2V 장문은 첫 화면을 모르면 움직임만으로 바꾼다.** 첫 화면을 못 읽었고(체크 해제, LoadImage 없음, 파일·시각 모델 실패) 도우미 결과도 없으면 장문은 빛·색·위치를 지어 쓰게 된다. 그 요청만 `wan22_i2v`(움직임만)로 쓰고 안내를 붙인다(프로필의 `fallback`). 첫 화면을 읽으면 시각 모델이 빛(`light`)과 색(`colours`)도 메모로 넘긴다.
- **참고 글의 간판.** 장문은 참고 글을 다시 쓰므로 모델에게 보여 주는 참고 글·첫 화면 메모에서만 간판 말을 바꾼다(결과의 장면 글은 그대로). 물건은 그대로 두고 글자를 부르는 말만 바꾼다: neon signs → neon lights, shop signs → shopfront boards, street signs → plain street panels, lit·glowing signs → lit·glowing panels. 처음에는 모두 '…lights' 로 바꿔서 도로 표지가 가로등이 되는 등 첫 화면 메모가 그림에 없는 빛을 말했다.
- **고쳐 쓰기 안내.** 한글이 섞이면 어느 단락인지 알려 주고, 카메라 이동이 둘이면 걸린 구절을 함께 보여 준다.

### 1인칭(POV) 요청

- 러다이트 파일럿 영상은 한국어 요청·계획·영어 프롬프트 모두 1인칭이었는데 결과는 조종사 뒷머리가 보이는 **어깨너머 샷**이었다. 러다이트 프롬프트는 'the seated pilot's eye position', 'the pilot's place at the controls' 처럼 조종사를 앉아 있는 인물로 썼다.
- 사용자 말 사전(`crew_intent.json`)에 1인칭 영상 의도를 더했다(1인칭, 1인칭시점, 일인칭, 주관 시점, 시점 샷, POV, first person, point of view, point-of-view / 확인어 first-person, first person, point of view, point-of-view, pov, through the eyes). 영상 렌더러만 이 말을 요구로 본다(사전 전체 163개, 영상 의도 15개). 사전 낱말 맞추기가 놓치는 '1인칭뷰', '1인칭으로만', '조종사·운전석·주인공·승객·내 시점' 은 `video.POV_RE` 로 따로 본다. '영상 내 시점 변화 없이' 처럼 '안' 을 뜻하는 '내'(영상·화면·장면·프레임·클립·컷·샷·씬 뒤)는 1인칭으로 보지 않는다. '1인칭 말고' 같은 부정은 다른 의도와 마찬가지로 가리지 않는다.
- 1인칭이면:
  - 사람이 있는 요청으로 본다('파일럿' 은 사람 말 사전에 없어서, 전에는 "사람을 넣지 말라" 지시가 붙고 손을 쓰면 위반이 됐다).
  - 지시: 카메라가 보는 사람의 눈이고 그 사람은 인물로 나오지 않는다, `shot` 은 "First-person POV from …" 으로 시작, 몸은 자기 손·팔뚝만 화면 가장자리에, 앉는다·입는다·바라본다를 쓰지 않는다, 화면 속 다른 사람은 그대로 쓴다. T2V 장문의 참고 글에 사람이 있으면 그 사람이 보는 사람이라고 알려 준다(이미지 도우미는 1인칭을 모른다).
  - 검사(`SELF_BODY_RE`): over the shoulder, behind the pilot, rear view of the driver, the pilot's head·headset, a view of a seated pilot, a seated pilot, camera … behind them, from behind them. 'a view of the pilot's own hands'(자기 손)와 'a view of the rider ahead'(앞사람)는 위반이 아니다. his·her·their 같은 대명사는 화면 속 다른 사람·배경에도 쓰여 보지 않는다.

### 검사 규칙 (장문에만 더한 것)

| 규칙 | 막는 것 |
|---|---|
| 단락 길이 | 네 칸 중 50낱말 미만인 칸 |
| 품질 유행어 | 8k, 4k, uhd, ultra hd, masterpiece, best quality, high quality, ultra·hyper·highly detailed, award-winning, trending on artstation (하이픈 표기 포함). 사용자가 직접 쓴 말은 막지 않는다 |
| 외형 반복 금지 | 장문에서는 적용하지 않는다 |
| 카메라·대상 방향 일치 | 대상이 멀어지는데 카메라가 뒤로 물러나며 같은 거리를 지킨다는 글(`blocking_problems`). 다가오는 대상 + 카메라 전진, 서 있거나 옆으로만 가는 카메라 + 같은 거리도 같다 |
| 카메라 항목표 (장문, 보통 제외) | `camera_light` 에 카메라 높이·각도(shot 단락에 있어도 됨)가 없거나, 카메라가 무엇을 유지하는지(거리·인물 크기·수평선·구도)가 없는 글 (`camera_sheet_problems`) |
| 깊이별 날씨 (장문, 보통 제외) | 비·눈·안개가 나오는데 한 문장도 가까이·중간·멀리(또는 'different depths')로 나눠 쓰지 않은 글 (`weather_depth_problems`) |
| 주변 입자 연결 (장문, 보통 제외) | 김·연기·먼지·불똥·꽃잎·물보라가 나오는데 한 문장도 빛이나 표면과 이어 쓰지 않은 글 (`ambient_link_problems`) |
| 움직이는 대상의 물리 묘사 (장문, 보통 제외) | 걷는·달리는 사람은 발·체중·착지와 전진·팔과 몸통 중 세 가지 이상 (`gait_problems`). 움직이는 동물은 발·날개, 체중, 딛고 치는 단계, 몸의 따름 중 세 가지 이상, 탈것은 바퀴·선체, 차체의 반응, 뒤에 남는 물보라·먼지 중 두 가지 이상 (`mover_problems`). 1인칭은 제외 |
| 이동은 한 속도 | 걷기·주행이 클립 중간에 '시작'하거나 느려져 '멈추는' 글(`travel_problems`). 시작은 T2V 만, 사용자가 출발·멈춤을 말했으면 보지 않는다 |

나머지(사용자 말, 한 컷, 카메라 이동 하나, 부정어, 글자·로고, 사람, 손 숨김, 영문만, 한국어 설명 3칸, 전체 낱말 수)는 기존과 같다. 다만 T2V 장문의 사용자 말에는 장르·색·조명·분위기 말이 더해진다.

#### 카메라·동선 일관성 (11-16 비교 평가에서 추가)

- 계기: 같은 요청(비 오는 미래 도시를 걷는 남자)에 대한 영문 프롬프트 3개를 글만 보고 비교했다(러다이트 에이전트 2개, 우리 워크플로우 1개). 우리 글은 첫인상이 가장 좋았지만 "카메라를 등지고 **멀어지는** 남자"와 "카메라가 **뒤로 물러나며** 일정한 거리를 유지"를 함께 썼다. 둘 다 서로 멀어지는 방향이라 거리를 지킬 수 없고 영상 모델이 어느 쪽을 따를지 알 수 없다. 또 "걷기 시작한다"·"걸음이 느려진다"가 있어 짧은 클립에서 출발·정지 동작이 어색해질 수 있다 [추정, 실제 영상으로는 아직 비교하지 않았다].
- 모델에게 주는 규칙(`long.rules`): 이동하는 대상은 카메라에 대해 어느 쪽으로 가는지 쓰고 모든 단락에서 카메라가 그와 맞게 한다(멀어지면 카메라가 뒤에서 앞으로 따라가고, 다가오면 카메라가 앞에서 뒤로 물러난다, 서 있거나 옆으로만 가면 같은 거리라고 쓰지 않고 대상이 작아지거나 커지게 한다). 이동 대상은 처음부터 끝까지 같은 속도로 움직이고, 차분한 마무리는 대상이 멈추는 것이 아니라 카메라가 자리잡는 것으로 만든다.
- 검사: `video.blocking_problems`(방향), `video.travel_problems`(시작·정지). 장문에만 켠다. 걸리면 기존 고쳐 쓰기 흐름을 따르고 `explain_ko` 가 한국어로 풀어 준다. 'a constant distance' 처럼 거리를 지킨다는 말이 있을 때만 방향을 본다. 안개·김의 drift 와 옆으로 나란히 따라가는 트래킹(러다이트 1번 글)은 걸리지 않는다.
- 아직 모르는 것 [TBD]: 정규식이라 'as the man walks off while the camera pulls away' 같은 변형은 놓칠 수 있다. 실제 생성에서 이 규칙이 뒷걸음질 결함을 줄이는지, 1·3번을 같은 모델로 뽑아 비교한 적은 없다.

#### 러다이트 1번 수준의 구체성 (11-16, 사용자 요청)

사용자 요구: 동선만이 아니라 러다이트 1번 글처럼 모든 것을 하나하나 분석한 완성도 높은 프롬프트가 나와야 한다. 1번 글이 한 일은 세 가지였다.

1. **카메라를 항목표처럼 정의하고, 무엇을 유지하는지까지 적는다.** 높이(eye-level), 이동 방식(lateral tracking shot), 속도(인물과 같은 속도), 대상과의 거리, 인물 크기, 수평선, 배경(자연스러운 시차).
2. **날씨를 깊이별 움직이는 요소로 쓰고 서로 잇는다.** 비를 배경 효과로 두지 않고 깊이별로 나눠, 건물·바닥 반사·빗방울·대기 원근감을 연결한다.
3. **인물의 움직임을 물리적으로 쓴다.** '걷는다' 대신 발의 착지, 체중 이동, 다음 발의 전진, 팔·몸통·옷자락의 따름을 구분한다.

- 모델에게 주는 규칙(`long.rules` 세 줄: Camera sheet, Weather and atmosphere in depth, Subject motion in physical terms)과 단락 정의(`camera_light`·`action` 의 `spec`, `spec_i2v`)에 위 세 가지를 넣었다. I2V 는 높이를 첫 화면의 각도로, 날씨·표면은 첫 화면 메모에 있는 것만 쓴다.
- 검사 세 개(`camera_sheet_problems`, `weather_depth_problems`, `gait_problems`)를 장문에 켰다. 걸리면 기존 고쳐 쓰기 흐름과 한국어 안내(`explain_ko`)를 따른다. **보통(mid) 프로필은 단락이 짧아 이 검사를 하지 않는다**(지시문 규칙은 그대로 본다).
- 검사는 있고 없음만 본다(정규식). 항목을 적었는지는 알 수 있지만 서술이 잘됐는지는 모른다.
- 시험: 러다이트 1번의 카메라·걸음·비 문장은 통과하고, 3번의 '비는 줄무늬로 내린다'·'걷는다'·카메라 한 줄은 걸린다. 기존 영상 테스트 58개는 그대로 통과(새 테스트 포함 62개).
- 모르는 것 [TBD]: 27B 가 항목을 다 채우면서 장문 낱말 상한(I2V 450, T2V 500 → 11-16 에 600)을 넘지 않는지, 고쳐 쓰기 1회로 충분한지는 메인에서 재야 한다. 규칙이 늘어 지시문이 길어졌으므로 `HELPER_NUM_CTX`(12288) 안에 드는지도 같이 본다.

#### 사람이 아닌 요청에도 같은 규칙 (11-16, 사용자 요청)

사용자 요구: 사람이 아닌 전혀 다른 영상 요청에도 같은 규칙이 똑같이 반영되어야 한다.

- 이미 모든 대상에 적용되던 것: 카메라 항목표(`camera_sheet_problems`), 카메라·대상 방향(`blocking_problems`, 동사 기준이라 대상이 무엇이든 본다), 이동의 시작·정지(`travel_problems`).
- 지시문 규칙을 대상 중립으로 고쳤다. 'Body motion' 을 **Subject motion in physical terms** 로 바꿔 사람(발 착지·체중·팔)뿐 아니라 동물(발굽·날개, 척추·꼬리), 탈것(바퀴·선체, 차체의 반응, 물보라·먼지·물결), 액체·천·불꽃·연기(어디서 시작해 어떻게 퍼지고 가라앉는지)를 단계별로 쓰게 한다. 'Weather and atmosphere in depth' 도 비·눈에서 안개·김·연기·먼지·불똥·꽃잎·물보라로 넓혔다. `action` 단락 정의에도 같은 예를 넣었다.
- 검사를 넓혔다: `weather_depth_problems` 에 안개, `mover_problems`(동물·탈것의 물리 묘사), `ambient_link_problems`(김·연기·먼지 같은 주변 입자를 빛이나 표면과 연결), 정지 검사의 대상에 동물·탈것을 더했다. 멈춰 있는 동물(자는 고양이)은 묻지 않는다. 1인칭은 보지 않는다.
- 한계: 검사는 사람·동물·탈것과 흔한 입자 낱말만 안다. 액체·천·불꽃·기계·식물 같은 나머지 대상은 지시문 규칙만 지키고 검사는 없다. 낱말 목록 밖의 동물·탈것은 놓친다. 영상 테스트는 64개(이 확장분 2개 추가)이고 모두 통과한다.
- 모르는 것 [TBD]: 27B 가 낯선 대상(기계, 식물, 추상 장면)에서도 규칙을 맞게 풀어 쓰는지는 메인에서 몇 가지 요청으로 봐야 한다. 주변 입자 검사('빛이나 표면' 낱말 목록)가 너무 느슨하거나 엄한지도 실제 글로 확인한다.

#### 메인 확인과 T2V 상한 600 (11-16)

허브의 `fix_video` 에 일부러 부실한 글을 보내 메인(PR #9·#10 반영 뒤)의 동작을 확인했다. 이 API 는 받은 글을 먼저 규칙으로 검사하므로 어떤 규칙이 서버에 있는지 위반 목록으로 알 수 있다(SSH 는 개발 PC 에서 막혀 있다).

| 시험 | 결과 |
|---|---|
| T2V 장문, 모순된 걷기 글(3번 프롬프트) | 방향 모순·출발/정지·카메라 높이·유지할 것·깊이별 비·걸음 묘사 6가지가 모두 걸렸다. 고쳐 쓰기 1회, 436낱말로 통과 |
| T2V 장문, 달리는 개(동물·탈것·입자 위반 섞음) | 세 가지가 걸렸다. 글은 낮은 높이·옆 트래킹·같은 속도·일정한 거리·수평선·시차, 앞발이 딛고 체중을 받고 다리가 휘둘러 지나가고 척추·꼬리가 따르는 묘사까지 좋았다. **542낱말이라 상한 500 초과**, 고쳐 쓰기 3회로 못 줄였다 |
| I2V 장문, 찻잔 첫 화면 | 고쳐 쓰기 2회, 317낱말로 통과. 카메라(테이블 높이·전진 돌리·일정한 거리·시차)와 김이 빛과 이어진 묘사가 나왔다 |
| I2V 장문, 비 오는 거리의 걷는 남자 | 355낱말. 눈높이·같은 속도로 물러나는 트래킹·일정한 거리, 발의 착지·체중·팔·몸통·코트 자락, 비를 '렌즈 가까이·중간·멀리' 세 층으로 쓴 글이 나왔는데도 **'비가 배경 효과'로 걸렸다** |

- 오탐 수정: 깊이별 날씨·주변 입자 검사가 문장을 세미콜론(;)에서도 잘라 'Rain falls in distinct layers: near the lens, …; in the middle, …; and far away, …' 의 앞 토막만 봤다. 마침표·느낌표·물음표에서만 자르고, 깊이 낱말에 distinct·many·three·two 를 더했다.
- T2V 장문 상한을 500 에서 **600** 으로 올렸다(사용자 결정). 목표는 410 에 그대로 둔다: 프로필의 `target` 으로 따로 정하고(`video.aim_words`), 지시문의 'aim for about 410' 과 낱말 수 안내('Cut it to about 410 words…')가 이 값을 쓴다. 목표를 범위 가운데(460)로 두면 27B 가 목표보다 25~60% 길게 쓰는 점 때문에 600 도 넘기기 쉽다. I2V 장문(250~450, 목표 350)은 355낱말로 문제가 없어 그대로다.
- Wan 의 텍스트 인코더는 글을 512토큰에서 자르지 않아 600낱말도 들어간다. 다만 긴 글이 짧은 글보다 나은지는 모른다 [TBD]. 같은 첫 화면·시드로 짧은 글과 긴 글을 뽑아 비교해야 한다.
- 이 시험은 한 요청당 한 번이다. 낱말 수는 실행마다 달라 상한 600 이 충분한지는 더 봐야 한다.

### 긴 글 때문에 함께 고친 것 (모든 프로필)

장문은 문장이 많아 짧은 글에 맞춘 검사가 엉뚱하게 걸렸다(1차 검토자 4명 + 검증자 16명, 2차 검토자 2명 + 검증자 6명, 11-11).

- 카메라 이동 개수: camera·drone 뒤 30자 안의 동사를 센다. 쉼표·and·as·while·when·until 에서 멈추되 바로 뒤가 카메라 자신의 다음 이동이면 계속 본다(", then tilts up", ", as it rises", ", the view rising"). 1차 수정은 관사가 있을 때만 멈춰서 'as steam rises', ', thin mist lifts' 처럼 관사 없는 다른 주어는 그대로 카메라 이동으로 셌다. 'camera left/right'(빛 방향)는 빼고, shot·lens 는 바로 뒤(then·-ly 부사는 건너뜀) 동사만 본다('a wide shot of rising mist' 는 이동이 아니다).
  - 확인: 메뉴 조합 15,500문장(이동 하나)에서 이동 둘로 잘못 센 수 HEAD 237 → 1차 191 → 2차 20(남은 20개는 진짜 카메라 항목), 관사 없는 주어 격자 2,592문장 오탐 1,566 → 0, 진짜 두 이동 24문장 중 놓침 1(30자 창 한계, HEAD 와 같음), 라이브러리 단독 판정·영상 의도 15개의 허용 이동 수 변화 0.
- 한 컷 검사: 'transitions to' 는 화면·장면(scene·shot·view·video·footage 등)이 주어이거나(사이에 seamlessly·then 같은 부사가 껴도), 뒤 세 낱말 안에 구도 말(close-up, view, shot, interior, exterior)이 오면 센다. 1차 수정은 주어 바로 뒤만 봐서 'The scene seamlessly transitions to', 'a smooth transition to a close-up' 을 놓쳤다. 빛의 변화('the light slowly transitions to warm gold')는 컷이 아니다. 'X, then transitions to soft rose' 는 HEAD 처럼 컷으로 본다(장면 전환을 놓치는 쪽이 더 나쁘다).
- 글자 검사(`crew.py`, 이미지 제작진과 공용): 'signs of wear·weathering·dawn·morning' 같은 관용 표현과 'brand-new·brand new' 는 글자가 아니다. 1차 수정의 'sign 뒤에 of 가 오면 뺀다' 는 'neon signs of nearby bars' 같은 진짜 간판도 놓쳐서 관용 낱말 목록으로 좁혔다.
- 사람 검사(공용): 'barista counter', 'man-made', 'human eye level·human scale', 'the figure of the bottle' 은 사람이 아니다. 'a lone figure', 'a figure of a woman', 'human hands' 는 계속 사람이다.
  - 확인: 라이브러리 12,744항목에서 글자·사람 판정이 HEAD 와 달라진 항목 0.
- 확인어(`crew_lib.terms_re`, 공용): 띄어 쓴 확인어는 하이픈 표기('pull-back', 'cherry-blossom')도 인정한다.
- LLM 문맥 길이: 허브 안 LLM 호출에 `num_ctx` 를 준다(`HELPER_NUM_CTX`, 기본 12288). T2V 장문은 지시문만 약 2,200토큰이고 답과 고쳐 쓰기 1회를 더하면 Ollama 기본(4096)을 넘어 지시문 앞부분이 잘린다. 한 GPU 차례 안의 호출은 같은 값을 써야 모델을 다시 올리지 않으므로 모든 허브 내부 호출에 같은 값을 준다.

### 검증과 모르는 것

- 단위 테스트 영상 46개(장문 관련 21개), 제작진 36개: 프로필 순서·표시, 네 칸 스키마, 단락 잇기, 지시문(예시·STYLE·모델 이름), 검사 규칙, T2V 장문의 장르 말, I2V 장문의 움직임만 대체, 1인칭 감지·검사, 카메라 이동 개수, 간판·한 컷·글자 검사, 고쳐 쓰기, T2V(장면 참고) 렌더, I2V(첫 화면 + 제작진 메뉴) 렌더, 2차 검토의 컷·카메라·간판·사람·1인칭 말·그림체·I2V 룩·루프 지시.
- **메인에서 아직 돌려 보지 않았다.** 확장 모델(qwen3.8:27b)이 네 칸과 300~450낱말을 지키는지, 고쳐 쓰기 1회로 충분한지 재야 한다 [TBD].
- ComfyUI 는 Wan 의 umT5 글을 512토큰에서 자르지 않는다(512 는 짧은 글을 채우는 최소 길이, `comfy/text_encoders/wan.py` 의 `max_length=99999999, min_length=512`). 그래서 450낱말(약 600토큰)도 모두 들어간다. 다만 Wan 은 512토큰까지로 학습했으므로 긴 글이 더 나은지는 모른다 [추정]. 첫 A/B(같은 첫 화면·시드로 움직임만 vs 장문)로 길이를 정한다.
- 영상 품질은 프롬프트 외에도 4스텝 LoRA(lightx2v)·해상도(지난 시험 640×640)·스텝 수에 크게 좌우된다. 렌더러는 이 설정을 바꾸지 않는다.

## 14. 첫 메인 시험과 패널 개선 (11-12)

### 첫 메인 시험 (I2V 장문)

- 요청 "비행기를 운항하는 파일럿의 1인칭 시점을 영상으로 만들어줘", 첫 화면은 ChatGPT 로 만든 조종석 이미지 한 장, 공식 Wan 2.2 14B 이미지→영상 템플릿(4스텝 LoRA 켬, 640×640, 5초, 81프레임·16fps).
- 렌더러가 네 단락(구도·카메라와 빛·움직임·마무리)을 썼고 첫 줄이 "First-person POV from the pilot's seat…" 였다. 파일럿의 뒷모습·어깨너머 표현은 없었다.
- 낱말 수는 423개로 I2V 범위(220~380)를 넘어 고쳐 쓰기 1회 뒤에도 경고가 남았다 [TBD: 상한을 450 쯤으로 올릴지 몇 번 더 보고 정한다].
- 영상은 한 번에 만들어졌다(5.06초). 앞으로 천천히 나아가며 구름이 흐르고, 화면 가장자리에 자기 손이 보이며, 첫 화면의 계기판·창틀이 유지됐다. 첫 화면에 이미 있던 왼쪽 가장자리의 사람 머리는 영상에도 남았다(외형은 첫 화면이 정한다).
- 시험 중 처음 열었던 워크플로우가 Fun Control 이라 "미디어 입력 누락(Load Video)" 오류가 났다. 이 템플릿은 참조 영상이 필요하다.

### 패널 개선

초보자가 영문 네 단락과 복잡한 그래프를 직접 다루지 않게 했다. 그래프를 다루는 로직은 `runtime/nodes/mgs_bridge/web/mgs_nodes.js` 로 분리했고 `hub/tests/panel_nodes.test.mjs` 로 시험한다(`node hub/tests/panel_nodes.test.mjs`).

| 문제 | 바꾼 것 |
|---|---|
| 규칙 경고가 영문이라 무엇을 고칠지 모른다 | 허브가 경고를 한국어로 풀어 준다(`video.explain_ko`, 응답의 `violations_ko`). 영문 원문은 마우스를 올리면 보인다 |
| 경고를 사람이 고쳐야 한다 | **자동으로 고치기** 버튼 → `POST /mgs/api/fix_video` → `video.fix`. 현재 글과 위반 목록을 모델에 주고 한 GPU 차례 안에서 고쳐 쓴다(최대 3회). 위반은 패널이 보낸 값이 아니라 허브가 다시 검사한다. 더 나아지지 않으면 원래 글을 그대로 둔다. 고치기 전 글을 이미 워크플로우에 넣어 두었다면 고친 글로 다시 넣는다 |
| 어느 노드에 넣을지 모른다 | **긍정 프롬프트 노드에 넣기**: 샘플러의 positive 입력에 이어진 글 노드를 따라가 찾는다(중간 노드·서브그래프 안까지). 선택한 노드가 있으면 그것이 긍정일 때만 쓴다. 공식 Wan 템플릿처럼 서브그래프의 `text` 입력이 열려 있으면 그 칸에 넣는다. 못 찾으면 선택한 노드에 넣고, 그것도 없으면 안내한다 |
| 긍정 프롬프트를 부정 노드에 넣는다 | 선택한 노드가 부정 노드면 알리고 긍정 노드에 넣는다. 사용자가 직접 부정 노드에 붙여 넣은 경우도 1초마다 지켜보다가(같은 글이 2초 머물 때) 긍정 프롬프트로 보이거나 패널이 만든 글과 같으면 알리고, 부정 노드는 이전 글로 되돌리고, 긍정 노드에 넣는다. 타이핑 중이거나 평범한 부정 목록 수정은 건드리지 않는다 |
| 짧은 요청에도 매번 네 단락은 과하다 | **사용자가 길이를 고르지 않는다.** 패널은 장문 프로필을 보내고 `auto_length` 를 켜며, 허브가 정한다(`video.decide_length`, 같은 GPU 차례 안). ① 요청이 3줄 이상이거나 공백 뺀 120자 이상이거나 '꼭 지킬 특징'이 있으면 모델을 부르지 않고 장문. ② 그보다 짧으면 LLM 에게 한 번 묻는다(JSON `tier` long·mid + 한국어 이유; I2V 는 첫 화면이 외형을 정하니 단순하면 보통, T2V 는 모습을 처음부터 만들어야 하니 아주 단순한 한 물건이 아니면 장문). ③ 못 정하면 요청 길이 규칙(짧으면 보통), 애매하면 장문이 기본. 보통은 같은 네 단락을 짧게(I2V 140~230낱말, T2V 170~260, 단락 최소 30, 밀도 예시 없음). 결과 카드에 "글 길이 자동 선택: 보통 (AI 판단) — 이유"를 보여 준다. 모델을 직접 고르는 '고급'은 그대로 있고 그때는 자동을 끈다. 한 줄 요청에서 장문이 보통보다 영상 품질이 나은지는 아직 비교하지 않았다 [TBD] |
| 이미지→영상인지 글→영상인지 모른다 | 열린 워크플로우의 노드 종류로 자동 판단해 모델을 고른다(점검 줄 "✅ 이미지 → 영상 워크플로우입니다 / ⚠ 참조 영상이 필요한 Fun Control 입니다"). 사용자는 길이도 고르지 않고(위 행) 모델 목록은 "고급"으로 접었다 |

- 긍정·부정 판단 순서: 샘플러 입력 이름(positive·negative) → 노드 제목 → 글 내용(품질 나쁨 나열이 2개 이상이거나 한자 부정 목록이면 부정). 글 내용으로 긍정을 가릴 때는 25낱말 이상의 영문 문장 둘 이상이어야 한다.
- 이미지 도우미(프롬프트 확장)의 결과도 같은 "긍정 프롬프트 노드에 넣기"를 쓴다. 이미지 도우미의 경고는 아직 영문이고 자동 고치기도 없다 [다음 후보].
### 두 번째 메인 시험 (패널 반영 뒤, 11-12)

- 확인됨: 점검 줄·자동 모델 선택·자세히/간단히가 보이고, 실제 템플릿의 서브그래프에서 긍정 칸(서브그래프 노드의 `text`)·부정 칸(안쪽 CLIP Text Encode)을 맞게 찾았다. 긍정 글을 부정 노드에 넣자 1~2초 안에 알림이 뜨고 부정 노드가 원래 글로 돌아갔다.
- 같은 요청으로 다시 만들자 이번에는 **475낱말**이 나왔다(첫 시험 423). 27B 가 목표(300)보다 25~60% 길게 쓴다. 고쳐 쓰기 1회와 자동 고치기 3회가 모두 380 이하로 못 줄였다. 모델은 낱말 수를 잘 세지 못하고, 처음 안내("write 220 to 380 words")는 얼마나 줄일지 알려 주지 않았다.
- 조치: I2V 장문 범위를 250~450, T2V 장문을 320~500 으로 넓혔다(목표는 중앙값 약 350·410). 낱말 수 위반 안내에 단락별 지금 낱말 수와 목표를 넣었다("Cut it to about 350 words in total, about 87 words per part (now: shot 130, …)"). 이 조치가 실제 모델에서 줄이는지는 메인에서 다시 확인해야 한다 [TBD].

- 메인에서 확인할 것: 서브그래프 구조가 템플릿마다 다를 수 있어(예: 입력을 열지 않은 템플릿) 긍정 노드를 못 찾는 경우가 있는지, 감시가 타이핑을 방해하지 않는지.

### 러다이트와 비교해 추가한 규칙 (2026-11-17, 비 오는 저녁 우산 쓴 남자 10초)

같은 요청의 러다이트 프롬프트와 비교해(스튜디오 요청 6b76e12e) 연출 설계 차이 7가지와 사용자가 고른 시간 구간을 넣었다. 검사는 `video.py`, 규칙 글은 `video_knowledge.json` 의 `long.rules`.

| 번호 | 바꾼 것 | 검사 |
|---|---|---|
| 1 | 움직이는 대상은 화면에서 가는 방향(왼쪽→오른쪽, 카메라 쪽 …)을 쓰고, 옆으로 가면 앞쪽에 여백. 장면 이미지 힌트에도 같은 말 | `direction_problems` |
| 2 | 고정(locked off) 카메라에서 다가오거나 멀어지는 대상은 화면에서 커지거나 작아진다. "크기·거리가 그대로"라고 쓰지 않는다 (옆으로 가로지르면 괜찮다) | `still_size_problems` |
| 3 | 걷는 사람이 우산·가방을 들었으면 어느 손이 어떻게 쥐는지 (손 숨김 요청은 제외) | `gait_problems` |
| 4 | 감정 낱말(dejected, sadness …)은 몸·시선 말과 함께 (고개·어깨·걸음으로 보여 주기) | `emotion_body_problems` |
| 5 | 빛이 인물을 배경에서 떼고, 따뜻한 포인트 광원 하나 (첫 화면이 있으면 첫 화면이 말한 빛만). 이미지 프롬프트 규칙 2번에도 | 규칙 글 (검사 없음) |
| 6 | 이미지 프롬프트 규칙 8번(손 숨김)의 소매 예시를 상시 규칙에서 빼고, 손 숨김 요청일 때만 사용자 글에 `HIDDEN HANDS` 블록으로 붙인다 (예시가 우산 든 남자의 장면에 새던 문제) | `promptx.HIDDEN_HANDS_BLOCK` |
| 7 | 소리 단락은 들리는 것만 (bokeh·glow·reflection 같은 눈에만 보이는 말은 위반) | `sound_problems` |
| 8 | **시간 구간**: LTX 프로필은 action 단락을 길이를 3등분한 구간으로 연다 (10초 → `From 0 to 3 seconds`, `3 to 7`, `7 to 10`; 20초 → 0-6, 6-14, 14-20; 5초 → 0-2, 2-4, 4-5; 5초 미만은 나누지 않는다). 첫 구간은 시작 순간, 둘째는 한 가지 주 동작, 셋째는 끝맺음 | `timeline_problems` |

- 실제 요청 6b76e12e 의 프롬프트에 새 검사를 돌리면 2·3·4·8 과 방향(1)이 모두 걸린다 (시험으로 고정).
- Wan 프로필은 구간을 쓰지 않는다 (시간 규칙의 "타임스탬프 금지"는 `TIMELINE` 줄이 있을 때만 예외).
- 구간은 LTX 가 숫자를 정확히 읽는다는 보장이 아니다. 움직임의 순서를 모델에 알리는 용도이고, 효과는 메인 시험으로 본다 [추정].
